# 对「0.3.1 推荐方案」的对抗式审查（含修正后的方案）

日期：2026-10-13　被审对象：research/12-0.3.0-adversarial-review.md 第四节的推荐方案
审查方式：先查事实（版本状态、接口能力、契约原文），再按第一性原理逐条攻击

## 总判定

原方案**方向对、判据错、估时虚、漏了根因**，且有一处会白做一版：

1. **版本号错**：0.3.0 根本没发布（`npm view dsh-log versions` = `0.2.0 / 0.2.1 / 0.2.2`；`.tmp-publish-status.json` 停在 0.2.1），所以「0.3.1 补丁版」是凭空的——应该在 0.3.0 内修完，**只发一次**。
2. **优先级判据错**：原方案按「审查者给的级别」排序，而不是按第一性原理判据（静默？不可逆？频次？修法成本？）。
3. **D1 的修法治症状**：真正的病是「读写两侧各自用正则猜文件名」，不是「正则写窄了」。
4. **sampleRate 推荐错了**：我推荐「实现采样」= 给一个没人要求的功能新增一条丢行通道，与「error 永不丢」正面冲突。
5. **0.4.0 是无触发条件的重构**：1651 行现在没造成任何功能问题，而它承载的是 9 轮审查才钉住的并发逻辑。
6. **最该做的一件事没做**：没质疑生成整类写侧风险的**接口**（`LogFileService` 只有整份覆写的 `writeText`）。
7. **估时不诚实**：「半天量级」低估了（见下）。

---

## 一、逐条攻击

### A1 版本号：0.3.0 未发布，「0.3.1」是白做一版

- 事实：`npm view dsh-log versions` → `["0.2.0","0.2.1","0.2.2"]`；仓库 `package.json` 是 0.3.0；`notes-publish-drill.md` 只记到 0.2.1。
- 攻击：0.3.0 从未对外的版本不存在「向后兼容一个已发布的坏版本」的问题。发 0.3.1 等于把已知缺陷的 0.3.0 也留在 npm 上，且多一次发布演练成本。
- 修正：**在 0.3.0 内修完，只发一次**。发布前按 `notes-publish-drill.md` 第三节的四项核对走（包内文档与仓库逐字一致、陌生机器装一次）。

### A2 优先级判据：应该按「静默 × 不可逆 × 频次 ÷ 修法成本」，不是按级别

按这个判据重排：

| 缺陷 | 静默？ | 不可逆？ | 频次 | 结论 |
|---|---|---|---|---|
| D1 封存件读不到 | 是（skipped=0 无提示） | 否（文件还在，可直接读） | **高**：任何一天超 5MB 就发生 | 第一 |
| D3 客户端丢 error | 是 | **是**（行真的没了） | 低：需要宿主 call 抛错 | 第二（唯一违反招牌承诺的一条） |
| D8 无类型 | 否（编译期大声报错） | 否 | **100%**：每个 TS 使用方 | 第三（阻断采用，但可绕过） |
| D2 客户端多报丢弃 | 是 | 否（只是计数） | 中 | 与 D3 同批 |
| D4 sampleRate 死参数 | 是（配置面说谎） | 否 | 低 | 见 A4 |

原方案把 D1 排第一**结论对**，但理由是「级别最高」——理由换成「高频 + 静默」才站得住；而 D3 的位置从第三提到第二，因为它是唯一让 error 真的消失的一条。

### A3 D1 的修法：从「单源正则」升级为「单源解析器」

- 病根：写侧知道自己在写 `YYYY-MM-DD.log`、封存成 `YYYY-MM-DD.N.log`；读侧只知道「匹配某个正则的文件名」。**两侧没有共享的「这一天有哪些文件」模型**，所以任何一侧改命名，另一侧静默错。
- 修正：`config.ts` 导出**一个解析器** `parseLogFileName(name) → { date, seq, sealed } | null`，四个消费者共用：
  1. 写侧封存（判断当前可写文件、算下一个序号）
  2. 查询/导出（可读集合）
  3. 保留清理 `retainSweep`（按 date 判 cutoff）
  4. `logClear` 的保护集与可删集
- 顺带修掉字典序错：`matched.sort()` 现在会把 `2026-10-13.10.log` 排在 `.2.log` 前面。按 `(date, seq)` 数值排序才对（对 traceChain 无害，但 epoch 指纹与导出顺序会因此稳定）。
- **原方案验收线写错了一处**：我写的「A3 清空语义按契约：`logClear({date:'all'})` 删得掉封存件」与契约冲突——契约说「当日文件永不删」，而 `isProtectedLogFile` 对 `today + '.'` 前缀的保护恰好覆盖当日封存件。正确表述是：**往日封存件可删、当日封存件仍受保护**。票 #25 的 A3 要按此改写。

### A4 sampleRate：删参，不要实现

- 攻击：实现采样 = 新增一条「普通行按比例消失」的通道。它立刻带来三个必须回答的问题：采样掉的行算不算 `dropped`？算不算 `onDrop`？和 `error 永不丢` 的边界在哪？——这正是 0.3.0 花 9 轮审查才收敛掉的那类语义泥潭。
- 需求侧：没有任何调用方要求它；客户端那侧的采样（只影响 debug 建链）已经覆盖了「高频 debug 拖垮链路」的真实诉求。
- 修正：**从 `setSwitch` 契约里删掉 `sampleRate`**（0.3.0 未发布且已是断裂版，删参零成本），开关文件形状退化为 `{enabled, rev}`，README/INTEGRATION 同步。若将来真有人要采样，再作为独立特性设计。

### A5 漏掉的根因：`LogFileService` 只有整份覆写，没有追加原语

- 事实（已核）：`LogFileService` = `resolve / readText / writeText / mkdir / unlink / listDir / rename?`——**没有 append、没有 stat**；`node.ts` 的 `createNodeFileService` 用 `node:fs/promises`（`writeFile`），而 `appendFile` 就在手边。
- 第一性原理：正因为只有整份覆写，「两个写者」才会从「丢一行」升级为「丢一整篇快照」，也才有「同目录只许一个活跃写者」「跨进程零保护」「200ms 租约预算」「冲突自愈」这一整套复杂度；每一次 flush 还要把整个当日文件重写一遍（5MB 上限下最坏每次 5MB 写）。
- 修正：给 `LogFileService` 加**可选能力** `appendText?(target, text)`（与已有的可选 `rename` 同构，能力协商、缺失即回退现状）：
  - 有 append → 追加写：不再整份覆写；跨进程风险从「整篇被吃掉」降为「交错但都在」；5MB 阈值变成纯尺寸问题（尺寸来源可用 `listDir` 条目已有的 `size` 或加可选 `stat`）；每次 flush 的写量从 O(文件) 降到 O(新增)
  - 无 append → 现状不动（DSH 宿主是否提供 append 未知，所以必须可选）
- 这一条比修 12 个缺陷更能**消灭一类缺陷**，也是唯一一条真正回应「第一性原理」的架构改动。代价：能力协商 + 一组新测试 + 阈值判据改写（约 1~2 天，不建议和 Track 1 混在一起发）。

### A6 0.4.0 的大重构：不做；只做 10 行的可注入注册表

- 攻击：`store.ts` 1651 行现在**没有**造成功能缺陷、没有造成测试失败、没有造成发布问题。它承载的是隔离登记 + 队列 + 重试 + 轮转 + 审计——9 轮对抗审查才钉住的并发逻辑。在没有触发条件（比如「要加第二种存储后端」「要实现跨进程锁」）时重写它，是把已验证的复杂度换成未验证的复杂度，收益只是「以后改起来更舒服」。
- 修正：把 0.4.0 降级为「**当某个具体改动真的需要时再做**」。真正值得现在做的是 10 行：`LogStoreDeps` 加可选 `registry?`，让调用方可以显式共享一份目录占用登记表——「模块副本级」从不可控的隐含行为变成可选显式行为（同进程多副本、热重载、测试并行都能自己决定）。
- 设计模式口径：这是依赖注入 + 显式边界，符合「最简单可行」；大重构是无触发条件的 YAGNI 违背。

### A7 方案修缺陷，但没修「让 D1 溜过去的流程」

- 攻击：D1 能穿过 118 例测试 + 37 条变异，说明缺的不是某条断言，而是**一类断言**：横跨读写两侧的不变式。原方案把它塞在 D1 的验收线里，等于一次性补丁。
- 修正：把它提为一等公民——**接缝不变式测试**：对「正常写 / 触发封存 / 保留清理 / 手动清空 / 跨天」每个场景，断言「磁盘 .log 里的本桶行集合 === 查询能看到的行集合（按 (ts,event) 多重集比较）」。它比任何单点修复都值钱，也是唯一能防止同类问题换张脸再来的东西。

### A8 估时：原方案「半天量级」是拍脑袋

| 工作 | 诚实估时 |
|---|---|
| D1 解析器 + 四处改用它 + 4 条验收 + 1 条变异 + 文档 | 1 天 |
| D2+D3 客户端重试状态机 + 3 条用例 + 改 M32/M33 锚点 | 0.5~1 天 |
| D8+D9 类型发行（构建 + exports + ambient 决策 + 消费方验收） | 0.5~1 天，且 D9 是开放决策 |
| D4 删参 + 文档 | 0.5 小时 |
| 每轮全量回归（118 例 + 变异表 37 条 + dist 重建） | 每轮 20~30 分钟，至少 3 轮 |
| **合计** | **2~3 天**，不是半天 |

另：原方案把「README 两处照抄即错的示例」（`README.md:32` 的 `deps`、`README.md:39` 的 `phones`）归到「小修」，但「首日重量」正是这个项目的立项痛点之一——**文档不实比内部死 API 更贵**，应放进 Track 1 尾部（10 分钟的事）。

## 二、修正后的方案（三轨，按依赖关系而非严重度排）

### Track 1：正确性（发布阻断，先做，约 1.5~2 天）

1. `config.ts` 单源解析器 `parseLogFileName(name) → {date, seq, sealed} | null`；写侧封存、查询/导出、`retainSweep`、`logClear` 四处共用；按 `(date, seq)` 数值排序。
2. **接缝不变式测试**（A7）：五个场景下「磁盘本桶行集合 === 查询可见行集合」。
3. 客户端诚实与重试：`dropped += rejected`；失败批次 `unshift` 回队首 + 有界退避（照 store 的 `scheduleRetry`：次数封顶、定时器 `unref`）；同步改 M32/M33 锚点。
4. `sampleRate` 删参（A4）+ README/INTEGRATION 同步。
5. 文档诚实：修 `README.md:32`（`deps` 未定义）与 `README.md:39`（`phones` 未定义）、`tsconfig.json:10` 的 esbuild 注释。
6. 收尾：删 4 个 deprecated shim 或写进迁移节；`npm pack` 复核；按 `notes-publish-drill.md` 四项核对后**只发 0.3.0 一次**。

**验收**：`tsc` 0；全量测试绿（含新增接缝用例）；变异表全 RED（含新增「读侧退回只认当日文件」与两条客户端变异）；探针 `probe-seal-read` 从「14 行磁盘 / 5 行可查」变为「14 行磁盘 / 14 行可查、`removed` 按契约」。

### Track 2：采用面（可与 Track 1 并行，约 1 天）

7. 类型发行：`declaration + emitDeclarationOnly` 接入 build；`exports` 每子路径 `{types, default}`；**决策点**：`node-ambient.d.ts` 手写适配层（保持零 devDependency、核心不碰平台）**还是**加 `@types/node` devDependency（标准形状、但要防核心误用 Node 类型）。
8. 根入口决策：补 `"."`（建议指 `./node`）或在 README 明写没有。
9. 消费方验收：临时工程（`strict` × `Bundler`/`node16`）编译 0 错误，`log.store.log(...)` 有类型与返回值。

### Track 3：写侧根因（不阻塞发布，约 1~2 天，独立成票）

10. `LogFileService` 加可选 `appendText`（与可选 `rename` 同构）：有则追加写、无则回退；阈值判据改用 `listDir` 的 `size` 或可选 `stat`；配套能力协商测试与「交错但都在」的并发用例；完成后重写 README 的跨进程风险段（从「整篇可能被吃掉」变成「可能交错，但不丢整篇」）。
11. `LogStoreDeps` 加可选 `registry?`（A6 的 10 行），把「模块副本级」变成可选显式共享。

### 明确不做（附理由）

- **不拆 `store.ts`**：无触发条件的重构，拿已验证的并发逻辑换未验证的结构（A6）。
- **不实现 `sampleRate` 采样**：给没人要的功能新增一条丢行通道（A4）。
- **不做跨进程锁文件**：先看 Track 3 的 append 能力能否把风险降到可接受；能降就不需要锁。
- **不动已做对的东西**：按天分文件、rename 能力协商、keyset 游标、诚实回包、重试位、`synced()` 唯一动词、诚实边界文档、变异表 + 真子进程用例。

## 三、需要你拍板的两个取舍

1. **ambient 策略**：手写最小 `node:*` 适配层（保持 `types: []`、核心绝不碰平台类型）还是加 `@types/node`（标准、但核心可能被平台类型污染）？我倾向后者 + `types: ["node"]` 只在 `node.ts` 生效做不到（tsconfig 是全局的），所以实际是「手写适配层」更符合既有约束——但代价是以后每个用到的 Node API 都要手写形状。
2. **Track 3 的时机**：现在就做（能消灭一整类写侧风险，但会把发布推后 1~2 天），还是先发 Track 1+2 的 0.3.0、把 append 能力留到 0.4.0？我倾向**先发**，因为 append 是「减少未来风险」而不是「修当前缺陷」。
